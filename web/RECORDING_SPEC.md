## Decisions (LOCKED — 2026-06-04, by user)

> **HARD REQUIREMENT — REUSABLE / SONG-AGNOSTIC.** The recording leg must work for ANY
> song/project (next up: a parody with the cat "Gormur"). **Nothing song-specific may be
> hardcoded.** Derive backing duration, sample rate, channel count, and all paths from the
> *configured assets* (ffprobe + `cfg`). `167.69s` / `44100 Hz` are THIS song's values,
> discovered at runtime — never constants. Build `takes.py` to depend only on the backing
> (+ optional render), not on `cut.json` / lyrics / clips, so it drops onto the next song
> by pointing config at new files. The user will not budge on this.

**Mixing location: SERVER-SIDE** — the user's call ("server can suck up more juice than a
browser"). The AudioWorklet sample-accurate capture graft stays.

## Recommended approach

Approach 1 (MediaRecorder + FastAPI multipart + server-side ffmpeg mix) is the WINNER and the backbone, but with the judge's five grafts folded in so capture is sample-accurate and the contract stays clean. Net design: (1) CAPTURE via AudioWorklet PCM (graft from Approach 3) — NOT MediaRecorder — so there is no opus codec-priming delay and t0 is a real sample index, not a jittery rAF-polled video.currentTime. (2) The backing (no_vocals.wav) is decoded via decodeAudioData and played through a single shared AudioContext; the worklet's first quantum, counted in samples at the true AudioContext.sampleRate, IS t0 (graft from Approach 2's clock-master insight). The render <video> shows visuals/teleprompter but is SLAVED to the audio clock, never the timing master. (3) On stop the Float32 buffer is encoded to a 16-bit WAV (hand-rolled, zero-dep) at the ACTUAL context.sampleRate (never hardcode 44100/48000) and POSTed multipart to a managed Take collection. (4) Server ffmpeg does the deterministic, reproducible mix over no_vocals.wav (audio m4a) or over the render's VIDEO stream copied through (shareable mp4) — the CORRECT deliverable, no double-vocals. (5) Takes are first-class resources: list / star / PATCH latency_offset_ms / delete, with nudge-and-re-mix from the retained raw WAV (graft from Approach 3), so 'fix sync without re-singing' is a product feature. (6) Multipart rides the existing Orval mutator via a FormData branch IN src/api/client.ts (graft from Approach 3), so the generated createTake hook works directly. (7) Per-device latency comes from a one-time click-loopback cross-correlation calibration persisted in localStorage (graft from Approach 2), feeding latency_ms; a signed manual nudge slider is the human override. This keeps the heavy/reproducible work server-side and inside the typed Pydantic->OpenAPI->Orval->TanStack Query+Zod contract, mirroring the existing RenderManager/ProjectRepository idioms, while killing Approach 1's only real liabilities (opus priming + rAF anchor) at the source.

## Summary

A 'Takes' vertical slice that mirrors the existing render pipeline exactly. New backend abra_api/takes.py owns a FilesystemTakeRepository (behind a protocol, the only thing touching takes/) and a TakeMixer (a RenderManager clone: async ffmpeg subprocess, single-slot-per-take with a bounded semaphore, status state machine streamed into log_tail). New Pydantic v2 models in domain.py (Take, TakeCreate, TakeUpdate, TakeMixRequest, TakeMixStatus + literals) drive OpenAPI -> Orval -> TanStack Query hooks + Zod for free. Frontend records the user singing over the karaoke using an AudioWorklet PCM capture (sample-accurate, no opus priming delay), with the no_vocals backing played through a shared AudioContext as the single timing master and the render <video> slaved to it for the teleprompter. Latency is measured per-device by a click-loopback cross-correlation calibration (persisted in localStorage) plus a manual nudge; the take WAV is uploaded at its TRUE sample rate with the song-position anchor + latency, and the server's ffmpeg shifts ONLY the vocal so it lines up with the immovable backing. Deliverables: shareable MP4 (user vocals over no_vocals + render video stream-copied, +faststart) or M4A/AAC audio. Everything verified live: backing & render are both 44100 Hz (do NOT hardcode 48000); render audio is the FULLBLAST mix so the video path mixes over no_vocals.wav, never [0:a] of the render (no double-vocals); both ffmpeg recipes produce correct durations and faststart.

**Grafts folded in from runners-up:**
- GRAFT THE CAPTURE PRIMITIVE FROM APPROACH 3: replace Approach 1's MediaRecorder/opus capture with the AudioWorklet 'pcm-recorder' -> Web Worker WAV encoder. This removes opus codec priming delay and gives a sample-counted t=0, directly killing Approach 1's single biggest sync liability while keeping its correct server-mix and bounded concurrency. The winner should record raw WAV, not webm/opus.
- GRAFT THE SYNC ARCHITECTURE INSIGHT FROM APPROACH 2: do NOT anchor the take to video.currentTime read under rAF — I verified useVideoTime is rAF-polled and frame-quantized. Even with server-side mixing, drive the backing/capture from a single AudioContext sample clock and treat the worklet's first quantum (counted in samples at the true sampleRate) as t0, recording the sample index rather than a jittery currentTime float. Server still does the mix, but the anchor it receives is sample-accurate.
- GRAFT THE FORMDATA-IN-CLIENT.TS FIX FROM APPROACH 3: I confirmed the Orval mutator (src/api/client.ts customFetch) force-sets Content-Type: application/json on any body, which breaks multipart. Approach 3's fix (a FormData branch in client.ts so the browser sets its own boundary) is cleaner and more reusable than Approach 1's sibling uploadTake.ts helper — keep multipart inside the one typed mutator so the generated createTake hook works directly.
- GRAFT THE MANAGED-TAKES COLLECTION FROM APPROACH 3: list / star / PATCH latency_offset_ms / delete as first-class Take resources, plus nudge-and-re-mix from the retained raw. This makes 'fix sync without re-singing' a product feature, not just a recovery path, and the PATCH-offset model is the right home for per-device calibration.
- GRAFT APPROACH 2's CLICK-LOOPBACK CROSS-CORRELATION CALIBRATION as the per-device latency source feeding the server mixer's offset — it's the most rigorous of the three latency-measurement schemes; persist it per deviceId in localStorage and send it as latency_ms / latency_offset_ms.
- HARDEN THE SAMPLE-RATE CONTRACT (lesson from probing the media, not from any one approach): no_vocals.wav and render.mp4 are BOTH 44100 Hz, while browser capture defaults to 48000. Do not hardcode 48000 (Approach 1 defaults and Approach 3's aresample=48000 are sloppy). Let the server own canonicalization: record the true device sampleRate on the Take and aresample to the backing's actual 44100 at mix time.
- FIX THE DELIVERABLE BUG before shipping any video mode: the render mp4's audio track is the FULLBLAST mix (original vocals + backing), so mixing user vocals over [0:a] of render.mp4 (Approach 3's command) double-vocals the output. For video mode, mux user voice + no_vocals.wav as the new audio and -c:v copy ONLY the render's video stream — exactly as Approach 1 specifies. Adopt Approach 1's mix recipe, not Approach 3's, for the video path.

**Key tradeoff for the human:** WHERE THE MIX HAPPENS — server (Approaches 1/3) vs browser (Approach 2) — and you should decide it on REPRODUCIBILITY vs SYNC-PURITY, because that's the one axis where the brief and the physics pull in opposite directions. Server-side mixing (the winner) is reproducible, idiomatic to your existing render pipeline, reuses your media endpoints, always produces a reliable MP4, and keeps the mix in your typed/observable backend — but its sync ceiling is gated by the browser's capture clock and the rAF-polled video.currentTime anchor I confirmed in useVideoTime (mitigated, not eliminated, by raw-WAV capture + sample-counted t0 + re-mix). Client-side OfflineAudioContext mixing has genuinely superior, deterministic sync because it's the only design that treats the AudioContext as the timing master instead of the jittery video clock — but it sacrifices reproducibility (re-mixing needs the user's browser), reliability (Safari/WebCodecs muxing is uneven, deliverable degrades to WAV), and forces a browser-quality 44.1->48 double-resample given your real 44.1k media. My recommendation: ship server-side (winner) but graft Approach 2's clock-master insight into the capture stage so you get most of the sync benefit without giving up the reproducible, type-safe, server-owned pipeline the house standards demand."

## Domain models (Pydantic v2)

### `TakeStatus (Literal)`
= Literal['uploaded','queued','mixing','done','failed'] — lifecycle of the raw take resource

### `DeliverableKind (Literal)`
= Literal['video','audio'] — selects mp4 (vocals over render video) vs m4a (vocals over no_vocals)

### `MixState (Literal)`
= Literal['idle','queued','running','done','failed'] — mirrors RenderStatus.state exactly for Orval/Zod parity

### `TakeCreate`
latency_ms: float = Field(default=0.0, description='measured per-device round-trip; vocal shifted earlier by this'); record_start_song_sec: float = Field(default=0.0, ge=0, description='song-timeline position where capture t0 landed (sample-accurate anchor)'); sample_rate: int = Field(gt=0, description='TRUE AudioContext.sampleRate the WAV was written at; server canonicalizes'); channels: int = Field(default=1, ge=1, le=2); mime: str = Field(default='audio/wav'); kind: DeliverableKind = 'video'; consent: bool = False; label: str = '' — JSON 'meta' part of the multipart upload

### `Take`
id: str (uuid); status: TakeStatus; kind: DeliverableKind; created_at: datetime; latency_ms: float; record_start_song_sec: float; sample_rate: int; duration: float | None; size_bytes: int | None; starred: bool = False; label: str = ''; raw_url: str (computed_field -> /api/media/take/{id}/raw); mix_url: str | None (computed_field -> /api/media/take/{id}/mix when status==done)

### `TakeUpdate`
label: str | None = None; starred: bool | None = None; latency_ms: float | None = Field(default=None, ge=-1000, le=1000) — re-label / mark keeper / nudge offset WITHOUT re-recording (PATCH body)

### `TakeMixRequest`
kind: DeliverableKind | None = None (override take's kind); latency_ms: float | None = None (override for nudge-and-re-mix); backing_gain: float = Field(default=0.85, ge=0.0, le=2.0); vocal_gain: float = Field(default=1.0, ge=0.0, le=2.0)

### `TakeMixStatus`
state: MixState; take_id: str | None = None; job_id: str | None = None; returncode: int | None = None; log_tail: str = ''; output_url: str | None = None — structurally mirrors RenderStatus so the polling hook is identical in spirit

### `RecordingConfig`
backing_url: str = '/api/media/audio'; backing_duration: float; render_url: str = '/api/media/render'; backing_sample_rate: int; default_backing_gain: float = 0.85; getusermedia_constraints: dict (echoCancellation/noiseSuppression/autoGainControl false, channelCount 1) — one typed hydration payload so the client carries no magic constants

## ffmpeg mix command

```sh
VIDEO deliverable (primary, validated live — mixes user vocals over no_vocals.wav and stream-copies ONLY the render's video, so the fullblast original vocals are NOT doubled): ffmpeg -y -i "{render_path}" -i "{audio_path}" -ss {head_trim_sec:.3f} -i "{raw_wav}" -filter_complex "[2:a]aresample={backing_sr},adelay={delay_ms}|{delay_ms},apad[v];[1:a]volume={backing_gain}[b];[v][b]amix=inputs=2:duration=longest:normalize=0:dropout_transition=0,alimiter=limit=0.95[mix]" -map 0:v -map "[mix]" -c:v copy -c:a aac -b:a 192k -ar {backing_sr} -shortest -movflags +faststart "{out_mp4}".  AUDIO deliverable (m4a, validated): ffmpeg -y -i "{audio_path}" -ss {head_trim_sec:.3f} -i "{raw_wav}" -filter_complex "[1:a]aresample={backing_sr},adelay={delay_ms}|{delay_ms},apad[v];[0:a]volume={backing_gain}[b];[v][b]amix=inputs=2:duration=longest:normalize=0:dropout_transition=0,alimiter=limit=0.95[mix]" -map "[mix]" -c:a aac -b:a 192k -ar {backing_sr} -t {backing_duration:.3f} -movflags +faststart "{out_m4a}".  PLACEMENT MATH (server-side, from the persisted Take): backing_sr = ffprobe of cfg.audio_path (44100 here; NEVER hardcode 48000, the take WAV may be 48000 and aresample handles it). net_delay_sec = record_start_song_sec - (latency_ms/1000). If net_delay_sec >= 0: delay_ms = round(net_delay_sec*1000), head_trim_sec = 0.0 (-ss omitted). If net_delay_sec < 0 (vocal must advance): omit adelay, instead use atrim -> replace the take chain with "[N:a]aresample={backing_sr},atrim=start={abs(net_delay_sec):.3f},asetpts=PTS-STARTPTS,apad[v]". Optional graft: insert loudnorm=I=-16:TP=-1.5:LRA=11 after amix (before alimiter) for consistent kid-friendly level. The exact argv is logged into TakeMixStatus.log_tail and is fully reproducible from meta.json + raw.wav, so `just take {id}` regenerates any take offline.
```

## Latency handling

TWO independent offsets, both measured (never guessed) and applied server-side so the take lines up with the immovable backing. (A) DEVICE ROUND-TRIP LATENCY (output+air+input): one-time click-loopback cross-correlation in calibrate.ts — play a known click through the backing path with AEC OFF, capture the mic bleed, cross-correlate to find the lag in samples = true round-trip for this device. Persist as calibrationOffsetMs per deviceId in localStorage. Fallback when uncalibrated: (AudioContext.outputLatency + baseLatency)*1000. This becomes TakeCreate.latency_ms; the vocal is shifted EARLIER by it. (B) SONG-POSITION ANCHOR (sample-accurate, the key graft): the backing AudioBufferSourceNode.start(t0) defines backing-sample-0; the pcm-recorder worklet stamps each quantum with currentFrame on the SAME context clock, so record_start_song_sec is derived from the worklet's first-kept-sample index at the true sampleRate, NOT from the rAF-polled, frame-quantized video.currentTime (the bug the judge confirmed in useVideoTime). The render <video> is slaved to the audio clock purely for the teleprompter. A ~3s pre-roll count-in lets the AudioContext/worklet warm up so first-quantum jitter is discarded before t0. CAPTURE uses AudioWorklet PCM, not MediaRecorder, eliminating opus pre-skip (~80ms) priming delay. getUserMedia runs with echoCancellation/noiseSuppression/autoGainControl ALL false (AEC mangles sustained notes) + channelCount:1; HEADPHONES are a hard UX requirement so the backing never bleeds into the mic. SIGN HANDLING is explicit server-side: net_delay = record_start_song_sec - latency_ms/1000; positive -> adelay, negative -> atrim head. Because mixing is deterministic and the raw WAV is retained, a wrong offset is fixed by PATCH latency_ms + re-mix (nudge slider, +/-200ms, signed) WITHOUT re-singing. SAMPLE-RATE: the WAV is written at the true context.sampleRate and the server aresamples to the backing's actual rate (44100), so a 48k capture never plays slow/drifts.

### Managed Take Collection: AudioWorklet WAV capture + server-side ffmpeg mux  ·  mix=server  ·  effort=L
_Browser records a sample-accurate raw WAV take via AudioWorklet; the take plus an explicit latency offset and session metadata are persisted server-side as first-class Take resources you can list/replay/pick among; server ffmpeg mixes the chosen take over no_vocals.wav (audio) or over the render (shareable video) for download._

- **Recording tech:** AudioWorklet (AudioWorkletNode + a 'pcm-recorder' AudioWorkletProcessor module at /public/pcm-recorder.worklet.js) capturing raw Float32 PCM per 128-frame quantum at the device's native AudioContext.sampleRate — NOT MediaRecorder. Rationale: MediaRecorder yields Opus/WebM with codec priming delay and no sample-accurate t=0, defeating the sync requirement; AudioWorklet gives a contiguous, gap-free, sample-counted raw stream we control. getUserMedia opens with echoCancellation/noiseSuppression/autoGainControl all FALSE so the mic stream is not time-warped or gated (AEC adds variable delay and would try to cancel backing bleed). Final placement = capturedAtVideoTime - latency_offset_ms/1000: the voice is shifted EARLIER by the input latency so it lands where the user actually sang. Both values live on the Take model and are applied server-side by ffmpeg adelay/itsoffset, never baked silently into the samples.

Findings:
- WHY SYNC DRIFTS — there are TWO independent offsets, not one. (1) OUTPUT latency: the gap between when you tell Web Audio / the <video> to play sample 0 and when the speaker actually emits it. (2) INPUT/CAPTURE latency: the gap between sound hitting the mic and the sample landing in your JS buffer. Both are device/OS/driver dependent (typ. 20–300 ms combined; Bluetooth headsets can be 150–500 ms). If you naively start the recorder and the backing 'at the same time' and then overlay the two files at t=0, the voice lands LATE by (output + input) latency. You must measure this and shift the recorded take EARLIER by that amount before mixing.
- MediaRecorder is the WRONG tool for sample-accuracy. It gives you an encoded blob (webm/opus or mp4/aac) with NO reliable mapping from a sample index to the backing-track timeline. Its `start(timeslice)` chunk boundaries are not sample-aligned, the first chunk has codec priming/encoder delay (Opus pre-skip ~80 ms, AAC ~1024–2112 samples) baked in, and `mediaRecorder.start()` itself has unmeasured startup latency. You can get it ~roughly aligned but never sample-locked, and the encoder delay is invisible. Fine for a 'good enough, fix in post' demo; not fine for 'the take must line up with the backing'.
- AudioWorklet is the CORRECT tool. A MediaStreamAudioSourceNode(getUserMedia stream) -> AudioWorkletNode running in the SAME AudioContext as the backing track gives you raw Float32 PCM in 128-sample render quanta, all stamped on ONE monotonic sample clock (`currentTime` / `currentFrame`). Because capture and playback share the context clock, the relative offset between 'backing sample N' and 'mic sample M' is deterministic and recoverable — you record the context time at which you scheduled the backing's start and the context time of the first mic quantum, and the difference is your raw capture offset before device latency. You accumulate the Float32 chunks (transfer to main thread via the worklet port, or use a SharedArrayBuffer ring buffer for zero-copy) and assemble one contiguous mono PCM buffer.
- AudioContext exposes the device latencies you need to compensate. `AudioContext.baseLatency` (seconds) = the context's internal processing/double-buffering latency from a node to the output device — usually one render-quantum-ish (e.g. 0.0026–0.04 s). `AudioContext.outputLatency` (seconds, the important one) = estimated time from the audio leaving the context to the listener actually hearing it (includes OS/driver/hardware buffering); typically 0.02–0.2 s, can be larger on Bluetooth. There is NO standard `inputLatency` property; for the mic side you must either measure it empirically (loopback) or treat (outputLatency + a measured-or-assumed capture latency) as one combined fudge factor. Construct the context with `new AudioContext({ latencyHint: 'interactive' })` for low, predictable latency; do NOT use 'playback'.
- MEASUREMENT — two viable strategies, in order of robustness. (A) ACOUSTIC LOOPBACK CALIBRATION (gold standard, accounts for the full round trip incl. speaker->air->mic): with echo cancellation OFF, play a short impulse/click or a known chirp through the speakers at a known backing sample, capture via the worklet, cross-correlate the recorded signal against the reference click to find the lag in samples. That lag IS the total (output+air+input) latency for THIS device. Do it once per session, store it, subtract it from every take. (B) CLOCK-BASED ESTIMATE (no calibration UI): offset ≈ (outputLatency + baseLatency) on the output side; for the input side, Chrome/Firefox give a per-frame capture timestamp on the MediaStreamTrack you can compare to context.currentTime, otherwise assume a constant. (A) is bulletproof and the right 'do the hard thing' choice; (B) is the graceful fallback when the user won't run calibration. ALWAYS expose a manual nudge slider (±200 ms) as the final human override.
- ECHO CANCELLATION / NOISE SUPPRESSION / AUTO GAIN are designed for VoIP speech and actively SABOTAGE singing. echoCancellation (AEC) will duck/cancel the backing track bleeding into the mic AND chew up sustained vocal notes (it mistakes held notes for echo), producing warbling, dropouts and a 'underwater' sound. noiseSuppression gates breaths and quiet passages and adds spectral artifacts on vocals. autoGainControl pumps the level mid-phrase, destroying dynamics and making later mixing/normalization unpredictable. For a singing-capture app you MUST request `{ echoCancellation:false, noiseSuppression:false, autoGainControl:false }` in getUserMedia constraints. BUT THE TRADE-OFF: with AEC off and the backing played through SPEAKERS, the mic records the backing too (bleed/double-track). The clean fix is to REQUIRE HEADPHONES (backing in the ears, only voice in the mic) — surface a 'use headphones' prompt. If a user is on speakers with AEC off you'll get a muddy double of the backing; detect-and-warn rather than silently enabling AEC.
- THE 'KNOWN START SAMPLE' BACKING STRATEGY is the linchpin and you ALREADY have the asset for it: GET /api/media/audio serves no_vocals.wav (the instrumental). Fetch it as an ArrayBuffer, `audioContext.decodeAudioData()` into an AudioBuffer, play it via an AudioBufferSourceNode with `source.start(startTime)` where startTime is a context timestamp slightly in the future. NOW YOU KNOW THE EXACT CONTEXT TIME OF BACKING SAMPLE 0. The mic worklet stamps every quantum with context time too. So recorded-sample-to-backing-sample mapping is exact, modulo the measured device latency. This is strictly better than syncing to the <video> element (whose currentTime is coarse, ~quantized to frames, and whose audio pipeline latency is opaque). Play the backing through Web Audio for the RECORD step; you can still show the muted render <video> for visuals, synced to context time.
- COUNTDOWN / PRE-ROLL: schedule everything on the context clock in the future. At record-start, capture t0 = audioContext.currentTime + PREROLL (e.g. 3.0 s). Schedule 3 metronome 'beep' AudioBufferSources at t0-3, t0-2, t0-1 (or 4 beats at the song tempo — you HAVE beats.json/BeatGrid.tempo, so count in on the actual tempo). Start the backing at t0 and start treating mic quanta whose context-time >= t0 as 'backing sample 0' onward. The pre-roll gives the singer a count-in AND lets the AudioContext/worklet fully spin up (first-quantum jitter happens during the throwaway pre-roll, not the take). Discard or ignore any captured audio before t0.
- FINAL MIX / DELIVERABLE belongs on the BACKEND, not the browser — it matches the house pattern exactly (you already shell ffmpeg via build_v3.py + RenderManager). The browser's job is: capture clean mono vocal PCM + the single scalar offset, encode to WAV (trivial, just prepend a 44-byte header to the Float32->Int16 buffer) or upload raw PCM, POST to a new endpoint. The backend then uses ffmpeg to (1) shift the vocal by the measured offset using `adelay` (if voice is early) or `atrim`/`-ss` (if voice is late) — actually since voice is recorded LATE you trim its head by the latency, (2) loudnorm the vocal, (3) amix with no_vocals.wav for the audio-only take-home, and (4) optionally mux that mixed audio over Afhverju-Abra_fullblast.mp4 (the burned-karaoke render) with `-c:v copy` for the shareable video. ffmpeg 6.1.1 here has adelay/atrim/apad/amix/aresample/loudnorm/highpass all available (verified).
- SAMPLE-RATE LANDMINE: the AudioContext runs at the OS device rate (often 48000 Hz on Linux/most laptops, sometimes 44100). Your render's AAC is 44100 Hz stereo (verified via ffprobe), no_vocals.wav is the backing. Capture whatever the context gives you, WRITE THE WAV WITH THE ACTUAL context.sampleRate in the header, and let ffmpeg `aresample` to a common rate at mix time. Do NOT hardcode 44100 in the browser — if the context is 48k and you label the WAV 44.1k, the take plays ~8.8% slow and drifts progressively (a sync bug that LOOKS like a latency bug but isn't).
- TANSTACK QUERY / ORVAL INTEGRATION: the upload is a mutation. Add a Pydantic v2 `TakeUploadResponse`/`TakeInfo` to domain.py, a POST /api/takes route with operation_id 'createTake' returning that model, and a GET /api/media/take/{id} FileResponse (mirror media_render's range-supporting FileResponse). The PCM/WAV bytes go up as multipart/form-data (UploadFile) with the offset + sampleRate as form fields or a JSON sidecar — note Orval's generated fetch client is JSON-oriented, so for the binary upload either (a) call fetch directly through the existing customFetch mutator with FormData (it already skips Content-Type when body is set — but it force-sets application/json only when no Content-Type and a body exist, so pass FormData and DON'T set Content-Type so the browser sets the multipart boundary), or (b) base64 the small WAV into a JSON body if you want it fully inside the generated typed client. The mix/mux is long-running -> reuse the exact RenderManager state-machine pattern (idle/queued/running/done/failed + log_tail polled via GET status), don't block the request.

Gotchas:
- MediaRecorder's first chunk carries codec priming/encoder delay (Opus ~80ms pre-skip, AAC ~1024+ samples) that is invisible and not part of any latency you measured — it silently adds offset. This alone disqualifies it for sample-accuracy.
- Hardcoding 44100 Hz in the WAV header while the AudioContext actually runs at 48000 Hz makes the take play slow and drift progressively over the 167 s song — looks like worsening 'latency' but is a rate mismatch. ALWAYS write context.sampleRate into the header and let ffmpeg aresample.
- Leaving echoCancellation ON (the default!) to avoid speaker bleed will mangle sustained sung notes (AEC treats held notes as echo -> warble/dropouts). The constraints object MUST explicitly set echoCancellation:false, noiseSuppression:false, autoGainControl:false — passing audio:true gives you the VoIP-tuned defaults.
- With AEC off AND backing on speakers, the mic double-records the backing -> muddy phasey mix. The only clean answer is headphones; detect speaker use (you can't fully, so just require/strongly-prompt headphones) rather than silently re-enabling AEC.
- Syncing the recording to the <video> element's currentTime instead of the Web Audio context clock reintroduces opaque, coarse, frame-quantized timing and the media element's own audio-pipeline latency. Use the AudioBufferSourceNode start-time as the truth and (optionally) mute/slave the video to it.
- The offset is recorded-voice-is-LATE, so you remove time from the FRONT of the vocal (atrim/-ss by offset) — don't reflexively `adelay` it; adelay makes a late take even later. Sign errors here are the #1 'it's still off' bug. Make the nudge slider signed and labelled (negative = pull voice earlier).
- Orval's generated typed client speaks JSON; a multipart WAV upload won't ride the generated hook cleanly. Either push binary through the raw customFetch mutator with FormData (and do NOT set Content-Type so the browser writes the multipart boundary — the mutator only force-sets application/json when a body exists and no Content-Type is set, so omit it), or base64 a small WAV inside a JSON body to stay fully inside the typed client.
- SharedArrayBuffer (the zero-copy ring buffer between worklet and main thread) requires cross-origin isolation headers (COOP: same-origin, COEP: require-corp). The Vite dev server and the FastAPI media responses both need them or SAB is undefined. If you don't want to set those headers, fall back to postMessage-transferring the Float32 chunks from the worklet (a copy, but fine for one 167 s mono take).
- AudioContext starts 'suspended' until a user gesture (autoplay policy). The record button's click handler must `await audioContext.resume()` before scheduling anything, or t0 is meaningless and the first quanta are dropped.
- no_vocals.wav declared duration is 167.69s but the rendered mp4 is 167.46s actual (ffprobe). Mix/mux against a single canonical source (decide: backing length or render length) and `-shortest`/pad explicitly, or the video take-home will have a trailing audio/video length mismatch.
- Bluetooth headsets switch to the HFP (hands-free) profile when a mic is opened, collapsing playback to ~8–16 kHz mono telephone quality AND adding 100–300 ms latency that changes the moment you start capture. Detect and warn; recommend wired headphones for recording.

function encodeWav(samples: Float32Array, sampleRate: number): Blob {
  const buf = new ArrayBuffer(44 + samples.length * 2);
  const dv = new DataView(buf); let p = 0;
  const u32=(v:number)=>{dv.setUint32(p,v,true);p+=4};
  const u16=(v:number)=>{dv.setUint16(p,v,true);p+=2};
  const str=(s:string)=>{for(const c of s)dv.setUint8(p++,c.charCodeAt(0))};
  str('RIFF'); u32(36+samples.length*2); str('WAVE'); str('fmt '); u32(16);
  u16(1); u16(1); u32(sampleRate); u32(sampleRate*2); u16(2); u16(16);
  str('data'); u32(samples.length*2);
  for (const s of samples){const v=Math.max(-1,Math.min(1,s));dv.setInt16(p,v<0?v*0x8000:v*0x7fff,true);p+=2;}
  return new Blob([buf], { type: 'audio/wav' });
}

- amix default normalize=1 divides EVERY input by the input count, so a 2-input mix is half-volume and sounds wrong/quiet. You MUST pass normalize=0 and control levels yourself with volume= (and clamp with alimiter). This bites everyone first.
- The source render Afhverju-Abra_fullblast.mp4 is NOT faststart (moov after mdat, probed). If you stream-copy it without -movflags +faststart the browser must download the whole file before playback starts and seeking/range gets ugly. Always add +faststart on the output.
- MediaRecorder webm/opus blobs have NO reliable duration (format AND stream duration probe as N/A). Do not compute length or trim from container metadata. This is the root reason apad + (-shortest or -t) and a CLIENT-SUPPLIED signed offset are mandatory rather than optional.
- adelay needs one delay value PER CHANNEL. A mono browser take, after aresample to stereo, needs adelay=ms|ms (two values). A single value only delays channel 1 and you get a phasey/half-delayed result. Put aresample=44100 BEFORE adelay.
- -shortest clamps to the shortest FINITE mapped stream. apad makes audio infinite on purpose, so you need a finite bound: either -map the copied video (167.46 s) OR pass -t 167.69 for audio-only. apad WITHOUT a bound = an infinitely growing file; no apad = a hard dropout where the shorter input ends. Both failure modes are silent until you check the output duration.
- The backing wav (167.69 s) is ~0.23 s LONGER than the render video (167.46 s). For the video deliverable -shortest correctly clamps to the video, but for the audio-only deliverable decide explicitly whether to use 167.46 or 167.69 as the -t bound so the two deliverables match.
- libopus ALWAYS resamples to 48000 Hz internally (the preview .opus came out 48k even though inputs were 44.1k). Harmless for an opus preview, but if you ever chain an opus intermediate back into the 44.1k AAC video you incur an extra resample — encode straight to the final container from the [mix] label instead of round-tripping through opus.
- sidechaincompress consumes its key input, and a labeled filter output can be used exactly once. You MUST asplit the vocal into [voc_mix][voc_key] before feeding one copy to the ducker and the other to amix, or ffmpeg errors with 'Stream specifier matches no streams'. (Hit this live; fixed with asplit=2.)
- Bare .opus / audio/webm does NOT play in an <audio> element on iOS Safari. If you ship an audio-only take-home, encode AAC in .m4a (or mp3) — not opus — or iPhone users get a non-playable download.
- Re-encoding the take through opus->aac->... loses quality each hop and adds latency. Mix once from the original take blob + wav straight into the FINAL encoder for whichever deliverable; don't build an opus intermediate and then transcode it.
- Use absolute paths for the backing wav in the ffmpeg invocation: it is NOT in the repo root, it lives at ~/Downloads/separated/htdemucs/Aravisur/no_vocals.wav (note the non-ASCII 'i' in 'Aravisur' — config uses Path.home()/'Downloads/separated/htdemucs/Aravísur/no_vocals.wav'). Pass cfg.audio_path through, don't hardcode a relative name.

# Pydantic v2 domain model (drives OpenAPI -> Orval -> Zod). Mirror RenderStatus for the job status.
from enum import StrEnum
from pydantic import BaseModel, Field
class DuckMode(StrEnum):
    MANUAL = "manual"
    SIDECHAIN = "sidechain"
class OutputKind(StrEnum):
    VIDEO = "video"   # take-home mp4 (H.264 copy + AAC)
    AUDIO = "audio"   # take-home m4a (AAC)
class OverlayRequest(BaseModel):
    offset_seconds: float = Field(description="signed: + = take started late, - = early")
    backing_gain: float = Field(default=0.7, ge=0.0, le=2.0)
    duck: DuckMode = DuckMode.MANUAL
    output: OutputKind = OutputKind.VIDEO
